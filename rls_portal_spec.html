1. Title + Summary

Purpose of RLS in this portal

  • Enforce per-row access so that users see only data they are allowed to see, regardless of application bugs or misuse of the API.
  • Support multi-organization and multi-role users: the same user can be org_admin in Org A and guardian in Org B; RLS must respect the current org context and role when filtering rows.
  • Separate Platform Admin (global) from Org Admin (per-org): platform admins can see all orgs; org admins see only their org(s).
  • Protect guardian/athlete data: guardians see only athletes they are linked to (via athlete_guardians); org admins and coaches do not get expanded guardian-style access to other guardians’ children.

Key assumptions

  • Multi-org: One user can belong to multiple organizations via organization_members with one role per org (org_member_role: parent, coach, org_admin).
  • Multi-role: A user may be org_admin in one org and guardian (parent) in another; RLS checks must use org_id and role together.
  • Org context: The “current” org is determined by the application (e.g. selected org in UI or JWT/session). Policies use auth.uid() and derive org from the row (e.g. org_id, team_id → org) or from membership; there is no single “current_org_id” in the DB unless provided via RPC/session variable.
  • Athletes vs children: Canonical table is athletes (renamed from children). Some legacy tables may still reference children; policy logic should use athletes and athlete_guardians for guardian-based access.

Security principles

  • Deny by default: If no policy allows a row to be seen or modified, access is denied.
  • Least privilege: Each role gets the minimum access needed (e.g. coaches see roster/attendance but not payment amounts where specified).
  • Explicit grants: Every SELECT/INSERT/UPDATE/DELETE must be explicitly allowed by at least one policy for the acting role.

2. Role Definitions

Platform Admin Global User listed in platform_admins. Can view/manage all organizations, users, audit logs, feature flags. Sub-roles: super_admin, support_admin, finance_admin, ops_admin. RLS typically allows full access to tables when is_platform_admin(auth.uid()).

Can manage org settings, members (except other org admins), teams/seasons, fees, invites, and all org-scoped data. Cannot see other organizations’ data. Guardian data access is still limited: org admin sees all athletes in the org but does not get to see other guardians’ private data (e.g. payment details of another parent) unless explicitly allowed for admin duties (e.g. recording offline payments).
Coach Per org User has role = 'coach' in organization_members for that org. Can view/manage teams they are associated with (via org membership; “coached” teams may be org-wide or scoped by a coach–team link if present). Can see rosters, events, attendance, announcements. Guardian (Parent) Per org / per athlete User has role = 'parent' in organization_members and is linked to athletes via athlete_guardians with status = 'active'. Can see only their linked athletes and data scoped to those athletes (events, RSVPs, attendance, fees assigned to them, payments they made). Cannot see other guardians’ athletes or payment details.
Athlete Data subject Athletes are represented as rows in athletes (and legacy children). They do not have a separate login; access to athlete data is via Guardian, Coach, or Org Admin. “Athlete data access rules” below define who can see which athlete rows.
Member (implicit) Per org Any user with a row in organization_members for an org (any role). Used for “user has some access to this org” checks (e.g. user_has_org_access).

3. Org Context Model

How “current org” is determined

  • The database does not store “current org” for the session. The application (frontend or backend) chooses the active org (e.g. after login or org switcher) and passes org_id in queries or RPCs where needed.
  • RLS policies do not rely on a single global “current_org_id.” They derive org from the row being accessed (e.g. organizations.id, teams.org_id, fees.org_id) and then check whether auth.uid() has the required relationship to that org (member, org_admin, coach) or to the linked athlete (guardian).
  • For multi-org users, after “switching” org in the UI, all subsequent queries must be filtered by the selected org (e.g. WHERE org_id = :current_org_id). RLS then ensures that only rows the user is allowed to see within that org are returned.

Membership tables

  • organization_members: (org_id, user_id, role). Primary source for org-level authorization.
  • athlete_guardians: (athlete_id, user_id, org_id, status). Primary source for guardian–athlete relationship; use status = 'active' for “can access this athlete.”
  • team_memberships: (athlete_id, team_id, season_id, status). Links athletes to teams; used to scope “coach/org admin sees athletes on teams in org” and “guardian sees events for teams their athletes are on.”

5. Policy Matrix (per-table)

For each table: org scoping fields, CRUD by role, row filters, and notes. org_id is used consistently; where the schema uses organization_id, policies must align (prefer normalizing to org_id in schema).

TABLE: organizations

Description: Master org table. Scoping: id (org_id).

SELECT: Platform Admin: all. Org member: orgs where user_has_org_access(auth.uid(), id).

INSERT: Platform Admin only (or service role for signup flows).

UPDATE: Platform Admin: all. Org Admin: only where user_is_org_admin(auth.uid(), id).

DELETE: Platform Admin only (or restrict to prevent accidental deletion).

Notes: Multi-org user sees multiple rows (one per membership).

TABLE: organization_members

Description: Links users to orgs with role. Scoping: org_id, user_id.

SELECT: User: own rows (user_id = auth.uid()). Platform Admin: all. Org Admin: rows where org_id in orgs they admin.

INSERT: Platform Admin: any. Org Admin: only for their org, and role != 'org_admin' (cannot create other admins).

UPDATE/DELETE: Platform Admin: all. Org Admin: only for their org, cannot modify/remove other org_admin rows or self-remove last admin.

TABLE: platform_admins

Description: Global platform admins. Scoping: user_id.

SELECT/ALL: Only is_platform_admin(auth.uid()). Mutations via RPC (e.g. admin_add_platform_admin) with super_admin check.

TABLE: organization_invites

Description: Invite tokens for org membership. Scoping: org_id, email, token.

SELECT: Org Admin for that org; Platform Admin; or anyone for row where accepted_at IS NULL AND expires_at > NOW() (e.g. for acceptance page lookup by token).

INSERT: Org Admin for org_id; Platform Admin.

DELETE: Org Admin for that org; Platform Admin.

TABLE: users

Description: User profiles. No direct org_id on row; org membership is in organization_members.

SELECT: Own row (id = auth.uid()). Platform Admin: all. Org Admin/Coach: users who are members of orgs they have org_admin/coach role in (via organization_members).

INSERT: Handled by handle_new_user trigger (auth); or service role. No direct user INSERT from app with RLS.

UPDATE: Own row; Platform Admin for any.

DELETE: Typically Platform Admin or service role only.

TABLE: families

Description: Household grouping (legacy). Scoping: org_id.

SELECT: Org Admin/Coach for that org; Guardian: families that contain their linked athletes (via athletes.family_id). Platform Admin: all.

INSERT/UPDATE/DELETE: Org Admin for org; Platform Admin. Guardians do not create families directly in typical flow.

TABLE: athletes

Description: Athletes (children). Scoping: family_id (optional), linked via athlete_guardians and team_memberships to org/team.

SELECT: Guardian: only athletes where user_is_guardian_of_child(auth.uid(), athletes.id). Org Admin: athletes in org (e.g. via team_memberships → teams.org_id and user_is_org_admin(auth.uid(), org_id)). Coach: athletes on teams in org where user_has_any_org_roles(auth.uid(), org_id, ['coach','org_admin']). Platform Admin: all.

INSERT: Org Admin (for org-scoped flows); Guardian only if explicitly allowed (e.g. “add my child” RPC). Coach: optional per product.

UPDATE: Guardian: own linked athletes. Org Admin: athletes in org. Coach: typically no or limited. Platform Admin: all.

DELETE: Restrict: only Org Admin or Platform Admin; prevent if dependent data exists (team_memberships, fee_assignments, etc.).

Notes: Guardian sees only their linked athletes; org admin does not see “as guardian” for other parents’ children.

TABLE: athlete_guardians

Description: Links guardians to athletes per org. Scoping: org_id, athlete_id, user_id.

SELECT: User: own rows (user_id = auth.uid()). Org Admin: rows for athletes in their org (via team_memberships + org). Platform Admin: all.

INSERT/UPDATE/DELETE: Prefer RPCs (e.g. add_guardian_to_child, accept_invite). If direct: Org Admin for that org; Platform Admin. Guardian may INSERT for self when accepting invite (WITH CHECK user_id = auth.uid() and valid token).

TABLE: sports, programs, levels

Description: Org hierarchy: sports (org), programs (org + sport), levels (org + program). Scoping: org_id.

SELECT: Anyone with org access: user_has_org_access(auth.uid(), org_id). Platform Admin: all.

INSERT/UPDATE/DELETE: Org Admin for that org; Platform Admin.

TABLE: teams

Description: Teams belong to org. Scoping: org_id.

SELECT: Org Admin/Coach: teams in org where they have role. Guardian: teams where their linked athletes have team_memberships. Platform Admin: all.

INSERT/UPDATE/DELETE: Org Admin; Platform Admin. Coach: UPDATE only if product allows (e.g. event updates).

TABLE: seasons

Description: Seasons (org-scoped). Scoping: org_id, team_id (if present).

SELECT: Same as teams: org role or guardian via team_memberships. Platform Admin: all.

INSERT/UPDATE/DELETE: Org Admin; Platform Admin.

TABLE: team_seasons

Description: Junction team–season. Scoping: via team_id → teams.org_id.

SELECT: Same as teams (org access or guardian via team). INSERT/UPDATE/DELETE: Org Admin; Platform Admin.

TABLE: team_memberships

Description: Athlete–team–season membership. Scoping: team_id, season_id, athlete_id.

SELECT: Guardian: memberships for their linked athletes. Org Admin/Coach: memberships for teams in their org. Platform Admin: all.

INSERT/UPDATE/DELETE: Org Admin (roster management); Platform Admin. Guardian: no direct write (use RPCs if join requests).

TABLE: events

Description: Events (practice, game, etc.) per team/season. Scoping: team_id, season_id.

SELECT: Guardian: events for teams their athletes are on (via team_memberships). Org Admin/Coach: events for teams in org. Platform Admin: all.

INSERT/UPDATE/DELETE: Org Admin; Coach (UPDATE often allowed). Platform Admin: all. Guardian: no.

TABLE: event_rsvps, event_general_rsvps

Description: RSVPs per event/athlete or general. Scoping: event_id → team; athlete_id.

SELECT: Guardian: RSVPs for their athletes. Org Admin/Coach: RSVPs for events in org. Platform Admin: all.

INSERT/UPDATE: Guardian: for their athletes only. Org Admin/Coach: for events in org. WITH CHECK: same scope as SELECT.

TABLE: event_attendance (attendance)

Description: Attendance records per event/athlete. Scoping: event_id, athlete_id.

SELECT: Guardian: attendance for their athletes. Org Admin/Coach: attendance for events in org. Platform Admin: all.

INSERT/UPDATE/DELETE: Guardian: for their athletes. Org Admin/Coach: for events in org.

TABLE: announcements

Description: Team or org-wide announcements. Scoping: team_id, org_id (if present).

SELECT: Guardian: announcements for teams their athletes are on. Org Admin/Coach: announcements for teams/org they have access to. Platform Admin: all.

INSERT/UPDATE/DELETE: Org Admin; Coach (team-scoped). Platform Admin: all.

TABLE: fees

Description: Fee definitions per org. Scoping: org_id.

SELECT: Org Admin/Coach: fees in org (coach may see only metadata, not amounts if policy restricts). Guardian: published fees that are visible (e.g. all_parents or assigned to their athletes). Platform Admin: all.

INSERT/UPDATE/DELETE: Org Admin; Platform Admin. Coach/Guardian: no.

TABLE: fee_assignments

Description: Assignment of fee to athlete + parent. Scoping: org_id, athlete_id, parent_id.

SELECT: Guardian: only rows where parent_id = auth.uid() (or linked as guardian for that athlete). Org Admin: all in org. Coach: status-only view if allowed (no amount_cents); application or view can restrict columns. Platform Admin: all.

INSERT/UPDATE/DELETE: Org Admin; Platform Admin. Guardian: no (assignments created by org).

TABLE: charges, checkout_sessions, checkout_session_items

Description: Charges and checkout per org/parent. Scoping: org_id, parent_id, fee_assignment_id.

SELECT: Guardian: own checkout and charges (parent_id = auth.uid() or via fee_assignment they can see). Org Admin: all in org. Coach: no. Platform Admin: all.

INSERT: Guardian: own checkout (WITH CHECK parent_id = auth.uid()). Org Admin: charges/checkout for org. Platform Admin: all.

UPDATE/DELETE: Per product (e.g. Org Admin for refunds/cancel).

TABLE: payments, payment_allocations, refunds

Description: Payments and allocations. Scoping: org_id, parent_id.

SELECT: Guardian: own payments (parent_id = auth.uid()). Org Admin: all in org. Coach: no. Platform Admin: all.

INSERT: Service role / Stripe webhooks; or Org Admin for offline. Guardian: only via checkout flow (service role or RPC). UPDATE/DELETE: Org Admin (e.g. refund); Platform Admin.

TABLE: offline_payments, offline_payment_allocations

Description: Offline payment tracking. Scoping: org_id, parent_id, fee_assignment_id. Note: some schemas use child_id referencing legacy children; treat same as athlete for guardian scope.

SELECT: Guardian: own (parent_id = auth.uid()). Org Admin: all in org. Coach: no. Platform Admin: all.

INSERT/UPDATE: Org Admin; Platform Admin. Guardian: no.

TABLE: installment_plans, installments, installment_schedules; waivers; discount_codes, discount_redemptions; scholarship_*; org_payment_policies

Description: Payment configuration and ledger. Scoping: org_id.

SELECT: Org Admin: all in org. Guardian/Coach: only where product allows (e.g. installment_plans visible for reference). Platform Admin: all.

INSERT/UPDATE/DELETE: Org Admin; Platform Admin. Guardian: no (except discount_redemptions for own checkout if allowed).

TABLE: travel_plans

Description: Travel plans per team/season. Scoping: team_id, season_id.

SELECT: Guardian: for teams their athletes are on. Org Admin/Coach: for teams in org. Platform Admin: all.

INSERT/UPDATE/DELETE: Org Admin; Coach (if allowed). Platform Admin: all.

TABLE: uniform_kits, uniform_kit_items, uniform_submissions, uniform_submission_items

Description: Uniform kits and orders. Scoping: org/team/athlete.

SELECT: Guardian: submissions for their athletes. Org Admin/Coach: kits and submissions for org/team. Platform Admin: all.

INSERT/UPDATE/DELETE: Org Admin/Coach: kits and items; Guardian: own submission rows for their athletes. Platform Admin: all.

TABLE: tryouts, tryout_registrations, tryout_scores, tryout_teams, tryout_criteria

Description: Tryouts and registrations. Scoping: org_id, athlete_id.

SELECT: Guardian: registrations for their athletes. Org Admin/Coach: tryouts and registrations in org. Platform Admin: all.

INSERT/UPDATE/DELETE: Org Admin/Coach: tryouts and scores; Guardian: own registrations (if allowed). Platform Admin: all.

TABLE: parent_invites, join_links, join_requests, child_claim_tokens

Description: Invites and join flows. Scoping: org_id, team_id, email, token.

SELECT: Org Admin: invites/links/requests for org. User: own pending invites (by email/token). Platform Admin: all. Join links: anyone for active token (for join page).

INSERT/UPDATE/DELETE: Org Admin; Platform Admin. User: INSERT join_request (requested_by_user_id = auth.uid()); accept invite via RPC.

TABLE: stream_channels, stream_channel_metadata, huddle_notification_preferences, huddle_reports, huddle_audit_log

Description: Huddles (Stream Chat) metadata and preferences. Scoping: org_id, team_id, user_id_1/user_id_2 for DMs.

SELECT: User: team channels for teams they’re in (guardian via athlete or coach/org_admin); org channels for org_admin; DM channels where user is participant. Preferences: own rows. Reports: own or org_admin. Audit: Platform Admin only.

INSERT/UPDATE/DELETE: Org Admin create channels; users own preferences; reports by reporter; audit by platform only.

TABLE: feature_flags (per-org), feature_flag_platform_defaults, feature_flag_org_overrides, feature_flag_user_overrides

Description: Feature flags and license gating. Scoping: org_id for overrides.

SELECT: Platform Admin: all. Org Admin: own org’s overrides and flag definitions they’re allowed to see. Others: typically no or via RPC that evaluates flags.

INSERT/UPDATE/DELETE: Platform Admin. Org overrides may be updatable by Org Admin if product allows.

TABLE: license_tiers, feature_entitlements, tier_feature_assignments, entitlement_overrides, org_licenses

Description: License and entitlement model. Scoping: org.

SELECT: Platform Admin: all. Org Admin: own org’s license and entitlements. Others: no or via RPC.

INSERT/UPDATE/DELETE: Platform Admin (or service role for billing).

TABLE: audit_logs

Description: Platform admin audit trail (immutable). Scoping: actor, entity.

SELECT/INSERT: Platform Admin only. UPDATE/DELETE: deny (FALSE).

TABLE: event_logs

Description: Global event log (immutable). Scoping: org_id, actor_user_id.

SELECT: Platform Admin only. INSERT: authenticated (log_event is SECURITY DEFINER). UPDATE/DELETE: deny (FALSE).

TABLE: organization_settings, organization_*_settings

Description: Org settings. Scoping: org_id.

SELECT: Org Admin; Coach/Guardian if needed for product (e.g. visibility). Platform Admin: all.

INSERT/UPDATE/DELETE: Org Admin; Platform Admin.

TABLE: notification_outbox, rsvp_notification_outbox, uniform_notification_outbox, user_notifications

Description: Outbox and user notifications. Scoping: org/user.

SELECT/INSERT/UPDATE/DELETE: Typically service role or RPC; if exposed, user sees own notifications; org admin sees org outbox.

TABLE: athlete_imports, venue_insights, event_locations, recurring_event_patterns, recurring_event_instances

Description: Supporting tables. Scoping: org_id or team_id where present. Apply same pattern: org role or guardian via team/athlete; Platform Admin all.

8. Testing Checklist

  • Guardian: Cannot see other guardians’ athletes; cannot see other parents’ fee_assignments or payments; can see only own checkout_sessions and payments; can see events/RSVPs/attendance only for their linked athletes.
  • Coach: Cannot see athletes outside teams in their org; cannot see payment amounts (if restricted by policy or view); can see roster and attendance for teams in org; cannot create fees or refunds.
  • Org Admin: Can see all org data (teams, seasons, athletes, fee_assignments, payments in org); cannot see other orgs’ data; cannot create other org_admin members; cannot remove self if last admin.
  • Platform Admin: Can see all organizations, users, event_logs, audit_logs, feature flags; can perform admin RPCs per role (super_admin, etc.).
  • Multi-org user: After switching org in UI, queries filtered by new org_id return only that org’s data; RLS does not leak data from other orgs.
  • Insert flows: Org creation (platform or service role); fee creation and assignment (org admin); checkout and payment (guardian own, or service role for Stripe); join_request (user own); invite accept (user + token).
  • Webhooks / service role: Stripe webhooks and server-side writes use service_role and bypass RLS; ensure no anon/authenticated path allows forbidden writes.

9. Known Failure Patterns

FOR ALL policies blocking inserts: Use both USING (for existing row checks where applicable) and WITH CHECK for INSERT and UPDATE. If only USING is set, INSERT may succeed with rows that don’t satisfy the intended constraint.
  • USING without WITH CHECK: UPDATE policy with USING but no WITH CHECK can allow inserting or updating to values outside intended scope. Always add WITH CHECK for INSERT and UPDATE policies.
  • Missing org_id scoping: Policies that only check “user is org_admin” without tying to the row’s org_id allow access to all orgs. Always bind to row: e.g. user_is_org_admin(auth.uid(), table.org_id).
  • Inconsistent naming org_id vs organization_id: Schema may use organization_id in some tables. Policies must use the actual column name; normalize to org_id in schema where possible.
  • Stale org context: If the app caches “current org” and doesn’t refetch after switch, queries may still filter by old org. RLS will still restrict rows, but the app may show no data or wrong list. Ensure UI refetches after org switch.
  • Coach vs org_admin: Do not grant coach the same write access as org_admin (e.g. fee creation, member removal). Use user_has_any_org_roles(..., ARRAY['coach','org_admin']) only where both are allowed.
  • Guardian as org_admin: When user is both org_admin and guardian, guardian-style policies (e.g. “see only my athletes”) still apply to guardian primitives. Do not expand guardian visibility for org admins; keep “my linked athletes” strict.

10. Implementation Order

  1. Membership and helpers: Ensure organization_members, platform_admins, athlete_guardians RLS and helper functions (is_platform_admin, user_has_org_access, user_is_org_admin, user_has_any_org_roles, user_is_guardian_of_child, get_user_children) exist and are correct.
  2. Core org scoping: organizations, organization_invites, users (read policies).
  3. Athletes and guardians: athletes, athlete_guardians, families; then team_memberships, teams, seasons.
  4. Events and announcements: events, event_rsvps, event_attendance, announcements.
  5. Payments: fees, fee_assignments, charges, checkout_sessions, payments, payment_allocations, refunds, offline_payments.
